Tại Sao Phải Có Phân Hệ Evaluation?

So sánh hiện trạng trước và sau khi chuẩn hóa hệ thống thẩm định chất lượng

Business & Tech Value
❌ Trước Khi Có Evaluation (Đánh Giá Thủ Công)
⚠️ Đánh giá định tính: Mỗi người nhận xét một kiểu ("thấy prompt này hay", "output tạm được"), không có thước đo thống nhất.
⚠️ Rủi ro hồi quy (Prompt Regression): Sửa prompt để phục vụ task A vô tình làm hỏng chất lượng của task B mà không hề hay biết.
⚠️ Mù mờ về chất lượng thực tế: Repo Owner không biết skill nào trong 20 skills đang được dùng hiệu quả, skill nào người dùng phải sửa lại nhiều lần (rework).
⚠️ Không có Quality Gate: Ai sửa PR vào repo cũng merge được nếu không có lỗi syntax, chất lượng suy giảm theo thời gian.
✅ Sau Khi Có Phân Hệ Evaluation (Chuẩn Hóa Số Liệu)
✔ Thước đo định lượng 100%: Có điểm số rõ ràng (0 - 100), ngưỡng Pass Rate, tỷ lệ Rework Rate và phân tích từng tiêu chí.
✔ Bảo vệ chống hồi quy (Regression Shield): Chạy bộ benchmark tự động trước khi merge code; bắt 100% các lỗi nghiêm trọng.
✔ Ma trận sức khỏe (Health Matrix): Báo cáo tự động tổng hợp tỷ lệ pass của toàn bộ 20 kỹ năng theo chu kỳ tuần/tháng.
✔ Tự động đề xuất cải tiến: Phân tích lỗi chi tiết (thiếu Gherkin, thiếu ma trận kiểm thử, rò rỉ mã nguồn) để tinh chỉnh prompt chuẩn xác.

✦ System Architecture

Kiến Trúc Tổng Quan: 4 Trụ Cột Vận Hành

Thiết kế tách rời giữa Quá trình thực thi prompt và Quá trình chấm điểm thẩm định

Core Components
Trụ Cột 1 Rubric Gate
File evaluation.yaml tại mỗi skill. Quy định ngưỡng đạt, 4 chiều đánh giá, các phần bắt buộc và mẫu chống chỉ định (prohibited patterns).
Trụ Cột 2 Benchmark Suite
Thư mục benchmarks/ chứa test cases thực tế. Luôn gồm 2 biến thể: sample_good_output (mẫu chuẩn) và sample_flawed_output (mẫu lỗi cố tình).
Trụ Cột 3 CLI Engine
Bộ công cụ dòng lệnh evaluation/src/cli.ts. Chạy thẩm định cục bộ tốc độ cao, tính điểm có trọng số, hiển thị kết quả ANSI màu và gửi telemetry nếu bật cờ.
Trụ Cột 4 Ingestion Server
Máy chủ server/src/index.ts lắng nghe telemetry port 3456. Tự động lưu trữ và xuất báo cáo trực quan reports/weekly-*.html.

✦ Setup Walkthrough

Hướng Dẫn Thiết Lập Môi Trường Từ Đầu (End-to-End)

Các bước chuẩn bị môi trường chạy Evaluation nhanh chóng và chính xác

Prerequisites & Run
1. Yêu Cầu Môi Trường (Prerequisites)
• Node.js: Phiên bản v22.0.0 trở lên (Hỗ trợ cờ --experimental-strip-types để chạy trực tiếp file TypeScript không cần build qua tsc).
• Package Manager: npm hoặc pnpm tiêu chuẩn.
• Dependencies: Thư viện yaml đã khai báo trong package.json.
$ node -v # Đảm bảo >= v22.0.0
$ npm install
2. Cấu Trúc Thư Mục Thực Thi
Repo hỗ trợ thực thi từ thư mục con ai-skills/ hoặc thư mục root thông qua proxy scripts:
ai-skills/ ├── evaluation/ # CLI Runner & Rubric Judge Engine │ └── src/cli.ts # Điểm vào chính của evaluation ├── server/ # Central Ingestion Server │ ├── src/index.ts # REST API port 3456 │ └── src/cli-report.ts# Trình xuất báo cáo định kỳ ├── skills/ # 20 AI Skills độc lập └── reports/ # Báo cáo HTML/JSON đã kết xuất
3. Khởi Động Server Thu Thập Telemetry (Khuyến Nghị Chạy Nền)
Chạy lệnh sau trên terminal để khởi động Central Ingestion Server tiếp nhận số liệu đánh giá:
$ npm run server
✔ Server sẽ lắng nghe tại: http://localhost:3456
✔ Sẵn sàng nhận dữ liệu tại endpoint: POST /api/telemetry

✦ Specification Deep Dive

Giải Phẫu Cấu Trúc Rubric (evaluation.yaml)

Quy tắc thẩm định cấu trúc, trọng số điểm và các điều kiện trượt trực tiếp (Quality Gates)

Rubric Architecture
# skills/work-breakdown/evaluation.yaml skill_id: work-breakdown skill_version: "1.0.0" task_types: - id: wbs_planning name: "Work Breakdown & Story Slicing" required_sections: - pattern: "epic|tổng quan dự án" name: "Epic Scope Definition" severity: major - pattern: "user stor|stories|story slicing" name: "Vertical User Story Slicing" severity: critical - pattern: "dependencies|phụ thuộc" name: "Cross-team Dependencies" severity: critical prohibited_patterns: wbs_planning: - pattern: "cắt theo tầng|story chỉ làm fe|story chỉ làm be" issue_code: "horizontal_slicing_anti_pattern" severity: critical rubric_dimensions: - dimension: completeness weight: 0.30 - dimension: soundness weight: 0.35 - dimension: actionability weight: 0.20 - dimension: clarity weight: 0.15 scoring: pass_threshold: 80 scale: 100 critical_issue_behavior: "instant_fail"
1. Required Sections & Regex
Sử dụng Regular Expressions để kiểm tra sự hiện diện của các đề mục kỹ thuật bắt buộc mà không câu nệ cách đặt tên chi tiết.
2. Prohibited Anti-Patterns
Phát hiện lỗi nguy hiểm ngay lập tức. Ví dụ: Rò rỉ code DDL/SQL vào FRD, hoặc cắt story theo tầng ngang (Horizontal Slicing).
3. Cơ Chế Instant Fail
Dù điểm tính toán có trên 80, nếu dính bất kỳ lỗi critical nào thì kết quả vẫn bị đánh dấu là FAIL và yêu cầu Rework.
Quy chuẩn: 100% 20 skills đều tuân thủ đúng cấu trúc rubric schema này Slide 5 / 12
✦ Test Suite Deep Dive

Giải Phẫu Cấu Trúc Benchmark (benchmarks/*.json)

Bộ test case chuẩn với cơ chế đối chiếu kép: Good Baseline vs Flawed Anti-Pattern

Benchmark Schema
// skills/work-breakdown/benchmarks/tc-01-baseline.json { "id": "tc-01", "name": "User Onboarding Epic Breakdown", "task_type": "wbs_planning", "prompt": "Phân rã Epic Đăng ký và Xác thực người dùng mới thành các User Story triển khai được.", "expected_sections": [ "Epic Scope Definition", "Vertical User Story Slicing", "Cross-team Dependencies", "Complexity / Sizing Estimates" ], "sample_good_output": "# WBS: Epic User Registration\n## 1. Epic Definition\nCung cấp luồng đăng ký tài khoản tự phục vụ...\n## 2. Vertical Sliced Stories\n- Story 1 (P0): Đăng ký Email (Trọn gói UI + API)...\n## 3. Dependencies & Risks\nPhụ thuộc tài khoản SendGrid...\n## 4. Estimates & Milestones\n13 Story Points trong Sprint 24.", "sample_flawed_output": "# Chia task\nTask 1: Dev làm database. Task 2: Dev làm backend. Task 3: Làm frontend." }
💡 Tại Sao Cần Hai Mẫu Output Đối Chiếu?
Một bộ test chuẩn không chỉ kiểm tra "đầu ra tốt có đạt không", mà còn phải chứng minh "hệ thống có bắt được đầu ra lỗi hay không":
✔ sample_good_output (Golden Baseline)
Mẫu đầu ra lý tưởng thỏa mãn 100% rubric. Điểm đánh giá phải đạt từ 85 - 100 điểm (PASS).
✖ sample_flawed_output (Flawed Anti-Pattern)
Mẫu đầu ra cố tình mắc lỗi (thiếu mục, vi phạm anti-pattern). Bộ chấm điểm bắt buộc phải đánh trượt (FAIL) để chứng minh tính nhạy bén.
Mục đích: Đảm bảo bộ đánh giá không biến thành "bù nhìn" luôn cho qua mọi kết quả Slide 6 / 12
✦ Developer CLI

Bộ Lệnh CLI Runner & Các Chế Độ Đánh Giá

Cách chạy kiểm thử offline cục bộ và gửi telemetry lên Central Server

Terminal Ops
Lệnh Thực Thi (Command) Chế Độ Telemetry Mục Đích Sử Dụng
npm run eval Single Skill Offline Local Đánh giá nhanh skill mặc định (documentation-analysis).
npm run eval <skill-id> Single Skill Offline Local Chạy kiểm thử cho 1 skill bất kỳ (vd: npm run eval work-breakdown).
npm run eval:send Single Skill Opt-in Server Chạy kiểm thử và tự động gửi kết quả lên Ingestion Server qua port 3456.
npm run eval:all Batch (20 Skills) Offline Local Quét toàn bộ 20 kỹ năng trong kho, xuất bảng tổng hợp ANSI trực quan.
npm run eval:all:send Batch (20 Skills) Opt-in Server Đánh giá 100% kho skills và đồng bộ toàn bộ telemetry phục vụ báo cáo.
npm run report Report Engine - Kết xuất báo cáo định kỳ ra file reports/weekly-*.html.
Cờ Tùy Biến Nâng Cao (CLI Flags)
• --opt-in: Kích hoạt gửi event telemetry lên server.
• --benchmark=<tên_file>: Lọc chạy duy nhất 1 test case cụ thể.
• --server-url=<url>: Trỏ đến server staging hoặc production khác.
💡 Mẹo Cho Dev Khi Viết Prompt
Trước khi commit thay đổi prompt mới vào file SKILL.md, hãy chạy npm run eval <skill-name> để đảm bảo prompt mới không làm giảm điểm benchmark!
Trực quan: Terminal hiển thị bảng ANSI màu phân định rõ PASS (Xanh) / FAIL (Đỏ) Slide 7 / 12

Cơ Chế Telemetry & Central Ingestion Server

Thu thập số liệu phi tập trung, bảo vệ quyền riêng tư và tối ưu ngữ cảnh prompt

REST & Data Schema

POST http://localhost:3456/api/telemetry
{ "eventId": "a7b8c9d0-1234-4567-89ab-cdef01234567", "skillId": "documentation-analysis", "skillVersion": "1.0.0", "taskType": "prd_analysis", "result": "pass", "score": 92, "reworkRequired": false, "dimensionScores": { "completeness": 95, "businessSoundness": 90, "gherkinAndTraceability": 90, "clarityAndFormat": 95 }, "issues": [] }
🔒 Nguyên Tắc Bảo Mật Quyền Riêng Tư (Privacy-First)
Event telemetry KHÔNG lưu trữ nội dung prompt bí mật hay thông tin nhạy cảm của khách hàng. Server chỉ lưu trữ metadata, điểm số và mã lỗi (issue codes) để phục vụ phân tích kỹ thuật.
⚡ Zero Context Window Penalty
Quá trình gửi telemetry chạy nền bất đồng bộ (non-blocking). Token ngữ cảnh của model AI được bảo toàn 100% cho công việc chuyên môn của người dùng.
💾 Lưu Trữ & Backup
Telemetry được lưu trữ tại file log JSON Lines an toàn, sẵn sàng tích hợp ingest vào Datadog, Prometheus hoặc Elasticsearch khi lên môi trường Enterprise.

✦ Contributor Guide

Quy Trình 4 Bước: Thêm Evaluation Cho Một Skill Mới

Hướng dẫn từng bước thực chiến khi phát triển hoặc đóng góp một kỹ năng mới vào repo

Actionable Steps
1
Tạo Rubric YAML
Tạo file skills/<skill-name>/evaluation.yaml. Khai báo required_sections, prohibited_patterns và trọng số 4 chiều.
2
Viết Benchmark JSON
Tạo thư mục benchmarks/ và file tc-01-baseline.json. Điền đầy đủ prompt thực tế, sample_good_output và sample_flawed_output.
3
Test Cục Bộ Bằng CLI
Chạy npm run eval <skill-name>. Kiểm tra output: Mẫu Good phải đạt ≥ 80đ (PASS), Mẫu Flawed phải bị bắt lỗi (FAIL).
4
Gửi PR & Telemetry
Chạy npm run eval:send để đồng bộ dữ liệu lên Ingestion Server. Tạo Pull Request trên GitHub với đầy đủ bộ test cases.
⚠️ Lưu Ý Quan Trọng Dành Cho Contributors
Khi viết sample_good_output, hãy sử dụng kết quả markdown thực tế và chất lượng cao nhất mà bạn mong đợi AI tạo ra. Tránh dùng nội dung placeholder sơ sài vì hệ thống có bộ lọc kiểm tra độ dài tối thiểu (> 50 ký tự) và ma trận nghiệp vụ.

✦ Automation & CI/CD

Thiết Lập Quality Gates Trong Pipeline CI/CD

Tự động chặn Pull Request vi phạm chất lượng ngay trên GitHub Actions

DevOps & Quality Gate
GitHub Actions Workflow Mẫu
Cấu hình file .github/workflows/eval.yml:
name: AI Skills Quality Gate on: [push, pull_request] jobs: evaluate-skills: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: node-version: 22 - name: Install Dependencies run: npm install - name: Run Global Evaluation run: npm run eval:all
Quy Tắc Merge Pull Request (Merge Policies)
1. 100% Pass Rate trên Mẫu Chuẩn: Toàn bộ sample_good_output của skill được sửa đổi phải đạt điểm qua bài kiểm tra.

2. Zero Critical Issues: Không được xuất hiện các lỗi nghiêm trọng như rò rỉ mã nguồn, thiếu Gherkin criteria hay vi phạm anti-pattern.

3. Không Hồi Quy Toàn Cục: Lệnh npm run eval:all phải vượt qua toàn bộ các skill khác trong hệ thống.
Lợi Ích Cho Repo Owner
Tự tin review và merge code trong 30 giây mà không cần phải tự mình ngồi test lại từng prompt thủ công!
